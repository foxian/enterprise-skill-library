# 技能成员授权边界与候选查询契约

## 背景

技能管理页面需要同时支持组织技能和个人技能的成员授权。现有实现允许组织技能直接授权组织外用户，授权列表对团队不显示权限，并且团队与成员授权只能移除不能编辑；候选查询又依赖组织运营权限，导致拥有技能管理权的用户无法可靠选择授权对象。

## 决策

1. 组织技能的直接成员授权仅允许技能所属组织的当前成员。服务端必须验证目标用户的组织成员身份，不能仅依赖 Web 候选列表限制。
2. 个人技能的成员授权面向全平台已启用 Skill User，使用完整用户名精确查询并确认；不使用组织前缀，不展示邮箱等管理字段。
3. 拥有当前技能 Manage Permission 的用户可以通过技能上下文查询组织成员、自定义团队或个人技能的全平台用户候选，接口返回最小展示字段。
4. 团队与成员授权列表都显示对象及其显式“授权权限”。实际有效权限仍按所有来源取最高值。
5. 已有授权通过行内编辑修改权限，保存或取消必须明确；新增候选排除已有授权。重复提交由服务端拒绝并提示改用编辑。
6. 成员离开组织时撤销其在该组织技能上的直接成员授权；重新加入组织不恢复该授权。通过团队产生的权限随团队成员关系失效，重新加入团队后恢复。

## 理由与取舍

- 组织技能限制组织成员，使组织边界与成员授权候选一致，避免组织外账号获得组织资源的直接协作者权限。
- 直接成员授权和团队派生权限采用不同生命周期，避免离开组织后残留显式授权，同时保留重新加入团队后的正常继承关系。
- 显示显式授权而不是合并后的有效权限，才能让管理者知道当前编辑会改变哪一条授权来源；页面需同时说明有效权限可能来自其他来源。
- 候选查询按技能管理权授权，避免用户拥有技能管理权却因缺少组织运营角色被迫手工输入；返回最小字段以减少账号信息暴露。

## 影响

- 服务端需新增或调整技能上下文候选查询、组织成员校验、重复授权错误和组织退出时直接授权清理。
- Web 需增加团队权限列、行内编辑保存/取消、联想筛选和完整用户名展示；个人技能不得出现组织级控件。
- CLI 与内置 `esl-operator` 技能若暴露相关授权行为，必须同步更新其命令契约和文档。
- 需要覆盖个人技能、组织技能、组织外用户、成员离开/重新加入、重复提交及不同授权来源叠加等测试场景。

## 不采用的方案

- 仅在前端过滤组织外用户：不可靠，无法阻止直接 API 调用。
- 继续要求组织运营权限查询候选：与技能管理权职责不匹配。
- 用有效权限替代显式授权显示：无法表达具体授权来源，编辑结果容易被误解。

### 既有客户端兼容

Web 使用 `mode: create | edit` 明确区分新增和编辑，服务端串行处理同一技能的授权变更并拒绝重复新增。未携带 `mode` 的既有 CLI 设置请求继续保持幂等设置语义，不改变 CLI 命令或参数；非法 `mode` 被拒绝。
