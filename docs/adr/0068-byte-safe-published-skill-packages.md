# 字节安全的技能发布包与发布预演

Status: accepted

Issue #143 暴露了发布链路把二进制资源转换为 UTF-8 字符串的缺陷。已确认采用 ZIP 作为新 Published Skill Package 的容器，而不是继续以 JSON 文本承载所有文件；升级后的 CLI 同时支持历史 JSON 包。本文记录已确认的取舍与实现边界。正式发布从服务端固定 commit 读取源码；dry-run 在服务端返回 404 时允许使用客户端 Base64 回退。

## 已确认的决策

- 通用支持二进制资源，不按 Word 扩展名单独处理。除发布过程中明确需要解析或修改的文本外，文件保持原始字节。
- 新发布生成 ZIP；升级后的 CLI 兼容历史 JSON 包。修复前的 CLI 不保证支持新 ZIP 包，需要升级。历史包中已经丢失的字节不能通过兼容读取恢复，需从完好源码重新发布。
- 最终发布包的完整字节继续用于下载 checksum 校验；源文件与安装文件的字节一致性另行验证，不把两类校验混为一谈。
- `publish --dry-run` 复用正式发布的打包逻辑，临时构建 ZIP 并校验包结构；不推送源码、不保存正式包、不创建 Release 或发布标签，不安装依赖、不执行技能脚本，临时包仅存在于内存中。
- 回归验证覆盖以 .docx 命名的二进制样本、UTF-8 文本、旧字符串格式 JSON 包、包 checksum，以及 CLI 本地采集和服务端 Git 读取路径。

## 实现状态

- 已实现 ZIP 发布包，包内以 `esl-package.json` 保存元信息、以 `files/` 保存原始文件字节。
- CLI 安装器按包头兼容 ZIP 与历史 JSON；历史 JSON 只能恢复其已有的 UTF-8 字符串内容。
- 发布包 URL 使用 `.zip` 后缀，checksum 覆盖最终 ZIP 的完整字节。
- `SKILL.md` 仅在发布元数据调整步骤按 UTF-8 文本解析；Word、图片及其他资源不经过文本转换。

## 源码快照与实现边界

- 正式发布通过 Gitea Contents API 按固定 commit 递归读取文件字节，再生成最终 ZIP；当前不直接调用 Git archive 接口。安装时不重新从 Git 动态生成包。
- 本地预演回退通过 `git ls-tree` 和 `git cat-file` 读取固定提交，不采集未跟踪或忽略文件，不跟随工作区符号链接。仅在服务端返回 404 时回退。
- 符号链接和子模块拒绝打包；Git LFS 指针不会自动下载其外部内容，发布者应将资源作为普通 Git 文件提交。
- ZIP 使用固定时间戳和排序的文件路径，避免相同输入因打包时间产生不同 checksum。
- 当前回归使用二进制样本验证字节保真，尚未使用用户原始 Word 文件验证可打开性。

## 考虑过的方案

- JSON + Base64：可以无损保存二进制，也较接近当前协议，但保留自定义文件容器且带来编码体积开销；本次选择 ZIP。
- tar.gz：同样可以作为文件归档，但本次沿用已确认的 ZIP 选择，不增加并列的新发布格式。
- 清单加独立内容寻址文件：可作为未来缓存与文件复用的方向；修复 #143 不引入新的文件分发平台。

## 后果

发布和依赖包的格式识别、URL 生成、下载校验及安装恢复需一起适配，不能仅改根技能包。CLI 行为变化必须同步更新 `skills/esl-operator/SKILL.md` 及其 `references/`（ADR-0008）。临时打包成功不等于完整下载、安装链路已验证。

依赖冻锁继续使用 skillId、version 与 checksum，不要求迁移旧锁。下载依赖时优先尝试 ZIP 地址，仅在返回 404 时尝试历史 JSON 地址；权限错误、网络故障和 checksum 错误不会触发格式回退，安装记录保存实际下载地址。
