# 组织删除下沉到组织管理团队，且组织名在删除后归还名字池

Status: accepted

组织删除原先只允许 ESL Platform Administrator 执行（`DELETE
/api/admin/orgs/:orgName`，超管鉴权 + 手打组织名确认）。现改为：**组织管理团队
成员**即可从个人控制台发起删除（同样要求手打组织名确认），ESL Platform
Administrator 保留治理兜底。删除沿用既有的 **Organization Deletion State**
（`deleting` → 完成 / `delete_failed`）而非同步物理删除。同时，**删除完成后该
组织名归还扁平名字池**，可被新的组织或用户占用——这取代了「名字一经占用永久
不可复用」的直觉延伸。

## 背景与动因

1. 角色二分（ADR-0033）把"组织最高管理权"完整地交给组织管理团队，而当前
   组织创建者能建组织却删不掉自己的组织，只能求超管——治理权不自洽。
2. 删除要跨系统清理 Gitea Organization、其下仓库、Published Skill Package 与
   全部 DB 记录（tenant、团队显示名、邀请、申请等）。一锤子买卖会在半途失败时
   留下孤儿数据，因此需要可恢复的失败态。
3. 名字归还与技能侧的决定**理由不同**，必须分开论证：Deleted Skill 的
   Identity 不可复用，是因为它承载**安装在外的引用**（别人机器上的锁文件、
   安装目录指向它）；组织名不承载外部引用——组织删除时其技能一并消失，而
   服务端技能的查找键是 `sk_` 开头的 Skill ID，与 scope 文本无关（ADR-0032）。
   若组织名永不复用，名字池会被每一个已删组织立上永久坟头，而这是纯耗损：
   扁平名字池是组织名与用户名共享的稀缺资源（ADR-0032）。

## Considered Options

- **同步物理删除**：删除跨 Gitea 与 ESL DB 两个系统，同步实现下任一环节失败都
  只能留下半删状态且没有状态可查；弃。
- **组织名永久保留**：与技能 Identity 的保留式语义形式对齐，但组织名不承载
  外部引用，保留只带来名字池的永久耗损；弃。
- **仅组织创建者可删**：与 ADR-0033"组织管理团队持有该组织最高管理权"冲突，
  且创建者离开后组织将无人能清理；弃。

## Consequences

- `POST /api/orgs/:orgName/deletion`（或等价的个人控制台动作）替代现有的超管
  专属删除入口成为常规路径；超管入口保留为兜底。
- 组织名与用户名共享同一个扁平池，因此释放的名字**组织与用户都能抢**，包括
  与某个已删除组织同名的用户名——这是共享池的必然结果，不是缺陷。
- 已删除组织名下技能的 Published Skill Package 随删除消失；在外部已安装的副本
  不受影响（其身份是 `@<已删组织名>/<技能名>`，本地安装解析依赖 Skill ID 与
  锁文件，不重新回到平台上查找）。
- `CONTEXT.md` 的 **Organization Deletion State** 词条补入发起者、显式确认、
  超管兜底与名字归还；**Organization** 词条的组织名不可改名约定不受影响
  （不可改名 ≠ 不可释放）。
