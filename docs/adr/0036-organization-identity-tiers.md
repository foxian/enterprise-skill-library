# 组织内身份三档：普通成员、管理成员、所有者成员

Status: accepted（管理成员身份来源已被 ADR-0038 部分取代）

组织内身份从二值（是不是组织管理团队成员）扩为**三档**，且三档全部**由常设团队
成员身份推导**——普通成员 = 组织只读 ∪ 组织读写团队成员，管理成员 = 组织技能管理
团队成员，所有者成员 = 组织管理团队（Gitea Owners）成员；组织内仍不存储任何角色。
身份变更（提升、收回、自我降级、自我退出）下移为个人控制台**成员列表上的一等动作**，
只有所有者成员能做，ESL Platform Administrator 按治理兜底同款。本 ADR 取代 ADR-0033
中"组织管理团队不设独立术语指代'治理者的人'"一条；ADR-0033 的其余命题——平台角色
恒为二元、治理权是团队身份而非角色、Super Administrator 不参与组织——原样保留。

## 背景与动因

1. **二值身份逼出一句假话。** 今天成员列表把一个人的身份标成「组织管理团队」——
   拿**团队的名字**当**人的身份标签**。原因不是疏忽：ADR-0033 明确拒绝给"人"造词
   （`:65`「组织管理团队**不设独立术语**指代"治理者的人"」）。但界面一旦落地就必须
   给一个人挂标签，这个拒绝当场失效，剩下的是"一个人是一支团队"这种语法错误。
2. **「技能管理」这一档今天是空壳。** 全仓没有一处因为调用者属于 `all-managers`
   而给他额外能力：一切 manage 都从**仓库级授权**派生（`packages/server/src/routes/
   skills.ts:974-981`），组织命名空间下的技能管理权则来自 Owners 判定
   （`skills.ts:960`）。四种身份在权限上只实现了两种。
3. **提升能力早已存在，但没有正经入口。** `POST /api/orgs/:orgName/teams/:teamId/members`
   只校验"团队属于本组织"与"账号已注册"（`routes/org-console.ts:336-354`），**不拦
   owner 级团队**——任何所有者成员拿着 Owners 的 team id 就能把人提为治理者。而界面
   把四支常设团队整体过滤掉（`org-console.ts:172`），于是这条能力只能靠猜。更糟的是
   它对面（收回）规则完整：不能移除自己、至少保留一名（`organization-membership.ts`
   的 `checkOrgManagerRemoval`）。一对相反的动作，一半有规则一半是空白。
4. **超管兜底只有拆、没有建。** `routes/org-admin.ts` 13 条路由中，成员维度只有查看
   与移除。ADR-0033 说"确实无人可用的组织走整体删除"，但删除**不可逆**且连带毁掉
   整个技能库。"唯一手段"与"最后手段"之间差的正是这次补上的"指定新管理者"。

## Considered Options

- **把 Owners 放进团队管理页，复用通用团队加人**：少写一套服务端。但治理权的授予与
  收回属于**成员管理**，不属于"团队权限批量授权"——把组织管理团队混进技能授权载体
  里，会让一对相反的动作分居两个页面，规则只会继续只长一半。弃。
- **三档只做显示层**：实现最省。但管理成员在权限上与普通成员无任何差别，多挂一个
  标签只会误导——这是术语表最该拒绝的那种词。弃。
- **逐级降级**（所有者成员只能先降到管理成员）：看似谨慎，但身份变更**完全可逆**，
  逐级只制造两次操作和一个中间态。弃。
- **管理成员也能授予身份**：让技能管理者能生产更多技能管理者，权限在组织内部自我
  复制；若还能授予所有者成员，等于**管理成员能给自己造出删除组织的权力**。ADR-0033
  的"互管对称"只对**同级**成立，落在所有者成员之间就够了。弃。
- **超管兜底只能指定组织内现有成员**：最小权限。但"成员也走光了"的组织仍然只能
  整体删除——与"补上添加，删除才真正是**最后手段**"自相矛盾。弃。
- **回填后管理成员为空**：语义最纯。但现有「全员管理」共享会指向空集，且出现"这人
  能管技能、标签却说他不该管"的假身份。弃。

## Consequences

- `CONTEXT.md` 新增 **普通成员 (Ordinary Member)**、**管理成员 (Managing Member)**、
  **所有者成员 (Owner Member)** 三个词条；**组织成员 (Organization Member)** 改为三档
  的统称；撤掉「组织成员」下的 `_Avoid_: 普通成员`；「平台角色」补一句"组织内身份是
  常设团队成员身份的投影"。
- 成员加入组织时只进**组织只读、组织读写**两个常设团队；组织技能管理团队不再自动
  加入，它承载**管理成员**身份。
- **所有者成员自动兼任管理成员**——「全员管理」这类共享不会指向空集，也避免出现
  "身份标签低于实际能力"的假身份。
- **受保护团队**（Owners 与三个常设团队）不再接受通用团队加人接口；身份变更只能走
  成员列表的一等动作。界面本来就从不给这些团队加人（`GET /orgs/:orgName/teams`
  已整体过滤），这一步只是让接口与界面一致。
- ESL Platform Administrator 的组织侧兜底**新增写能力**，并可把组织外的人**空降**为
  所有者成员；空降必须同时把对方加入组织并补进组织只读、组织读写两个常设团队，否则
  会造出"不在组织里、却是组织所有者"的状态。
- 不变量收敛为一条：**组织必须至少保留一名所有者成员**。它统一覆盖被他人移除、自我
  降级、自我退出三种走法（超管兜底本就不破它）。**管理成员一档没有对应不变量**，
  允许为空——它是一个能力档，不是治理档。
- 存量按 ADR-0032 的 Bootstrap Reset 推倒重建，**不做迁移**：非管理成员移出
  `all-managers`。
- **本轮不含技能三轴**（可见性三值：私有 / 组织内 / 全平台；可写性：上限"组织内全员
  可写"；管理：含删除技能；三条轴上都能加自定义团队与自定义成员协作）。管理成员的
  技能管理权本轮仍**派生自所有者成员的共享动作、默认为零**，其能力边界留给那一轮定义
  ——因此本次不改 `skills.ts:960` 的组织命名空间判定。
- 治理变更的**审计留痕**不在本轮：全平台目前没有任何审计设施，单为这一个动作引入
  审计是错的粒度。
