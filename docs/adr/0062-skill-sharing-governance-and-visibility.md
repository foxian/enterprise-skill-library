# 技能共享治理与发布可见性解耦

Status: accepted

ESL CLI 需要覆盖技能作者与 Agent 管理已发布技能访问范围的日常闭环。技能可见性、显式授权和 Release 生命周期彼此相关但不是同一状态；清理授权不应隐式改变可见性，发布也不应夹带可见性变更。

## 决策

- `esl skill share`（及其资源命令路径）提供共享治理入口：查看技能权限矩阵；按团队或成员授予、调整及撤销显式权限；独立切换技能 `public/private` 可见性。
- 团队授权与成员授权均是针对单个技能的显式授权。权限矩阵展示这些授权；Server 负责权限判定、验证和持久化状态变更，CLI 只发起操作并呈现结果，不复制服务端授权规则。
- 保留一个明确清空该技能**全部显式团队与成员授权**的操作。命令名称、帮助和确认提示必须表达清空授权的范围；它不改变可见性，也不撤销所有者、Maintainer 或管理员基于角色获得的权限。
- `public/private` 可见性是独立于显式授权的技能状态。切换可见性不自动添加或删除授权；清空授权不等价于设为 `private`。
- 可见性变更不属于 Release 发布操作。移除没有实际生效的 `publish --visibility` 选项；`publish` 只处理 Release 生命周期，若要改变可见性，使用独立的共享治理操作。

## 考虑过的方案

- **清空授权时同时改为 private**：混淆两种独立状态，可能意外改变公开技能的消费者可见性，拒绝。
- **在 CLI 本地判定授权并维护一套策略**：会与 Server 的权限事实源分叉，拒绝；客户端只负责交互和传输。
- **把可见性作为 publish 参数**：将访问治理与 Release 生命周期耦合，且当前参数并未实际传递／生效，拒绝。

## 后果

- 作者可以在一处完成查看权限、配置团队／成员授权和切换可见性。
- “清空显式授权”是可预测且范围有限的治理操作，不会暗中改变公开状态或角色权限。
- CLI、内置 `esl-operator` 技能与 Server API 的命令及行为契约需要保持一致；任何 CLI 行为实现应同步更新该技能的 `SKILL.md` 和相关 references，并按仓库约定验证。
