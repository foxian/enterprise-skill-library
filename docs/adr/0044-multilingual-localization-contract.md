# Web 与 CLI 的中英文多语言契约

Status: accepted

ESL 需要同时支持 Web 管理后台与 `esl` CLI 的中文和英文，并让账户偏好、浏览器语言、临时覆盖以及 API 错误在不同客户端之间保持一致。系统采用统一的 `i18next` 方案和共享翻译资源；第一阶段支持 `zh-CN` 与 `en-US`，默认语言为 `en-US`。

## 决策

- 多语言范围覆盖 Web 管理后台和 `esl` CLI；用户创建的组织名、团队显示名、技能名、技能描述、发布说明等内容保持原文。
- 翻译资源、locale 类型、键校验与共享格式化工具放在独立的 `packages/i18n` 包中。Web 和 CLI 使用同一套语言包。
- 两种正式支持的 locale 为 `zh-CN` 与 `en-US`。翻译键使用英文、稳定且按领域分组的点号命名，例如 `auth.login`、`organization.memberRemoved` 和 `common.cancel`。
- 语言解析优先级为：
  `当前临时覆盖 > 账户 locale > 浏览器语言 > en-US`。
- 浏览器语言先精确匹配，再按语言主标签匹配：`zh-*` 映射到 `zh-CN`，`en-*` 映射到 `en-US`；其他语言以及没有语言信息时均使用 `en-US`。
- 账户 `locale` 是可为空的用户偏好。`null` 表示用户没有主动选择，不等于已经解析出的最终语言。
- Web 语言切换立即生效。登录用户的选择保存到其账户；未登录状态通过 Cookie 保留，以便登录页和登录响应返回前使用。
- Skill User 与 ESL Administrator Account 都支持语言偏好。登录响应返回当前账户的 `locale`，并提供独立的账户偏好读写接口。
- CLI 支持 `--locale <locale>` 作为当前命令的临时覆盖；登录后读取账户 locale 作为默认来源，但显式 `--locale` 不覆盖账户偏好。
- API 错误统一提供稳定的 `code`、插值用的 `params` 和固定英文的 `message`。Web 与 CLI 根据 `code` 和当前 locale 翻译；未知错误码使用 `message` 兜底。机器可读 JSON 的字段名、错误码、枚举值和技术标识不随语言变化。
- 第一阶段迁移现有 Web、CLI 和 API 用户可见文案。两套语言包的键集合必须完全一致；缺失或多余键在测试/构建阶段失败，运行时缺失翻译回退到中文文案。
- 日期、时间和数字按当前 locale 展示；API 存储格式、机器可读字段、Skill Identity、用户名、版本号和命令名保持稳定格式。

## 考虑过的方案

- Web 使用 `vue-i18n`、CLI 使用另一套实现：与 Vue 集成自然，但会产生两套运行时和格式化语义，难以保证客户端一致。
- 各客户端继续根据现有自然语言错误文本翻译：无法形成稳定 API 契约，文案调整会破坏客户端。
- 接入在线翻译管理平台：第一阶段只有两种语言，仓库内语言包和构建校验足够，暂不引入额外运营依赖。

## 后果

- `packages/i18n` 成为 Web、CLI 和未来客户端共享用户可见文案的边界。
- 服务端错误文案不再是客户端判断业务错误的依据；新增错误必须登记稳定错误码及参数。
- 新用户在完全没有语言信息时看到英文，这是有意选择的默认行为。
- 新增语言时需要扩展 locale 解析、语言包、组件库语言包和完整性校验，但不需要改变 API 的机器可读契约。
