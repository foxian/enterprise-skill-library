# 技能权限属于技能，逻辑团队只负责成员集合

Status: accepted

## Context

旧模型把自定义团队的 Git Backend permission 当作团队的固定属性。技能授权只需要
挂载团队，因此同一个团队在所有技能上只能拥有同一个权限档位。这无法表达同一团队
在技能 A 上只读、在技能 B 上读写的常见场景，也会让修改团队权限意外改变所有已授权
技能。

## Decision

自定义团队在 ESL 中建模为不携带技能权限的逻辑团队。Git Backend 为每个逻辑团队
维护三个内部权限团队，分别表示 Read、Write 和 Manage。技能授权记录保存
`(skill, logical_team, permission)`，并将对应的内部权限团队挂载到技能仓库。

同一技能、同一逻辑团队最多存在一个权限档位。变更档位只替换当前技能的内部团队
挂载。成员变更同步三个内部团队，因此不同技能可以独立使用同一逻辑团队。

固定组织团队 `all-readers`、`all-writers`、`all-managers` 继续保留，它们不是自定义
逻辑团队，也不参与三内部团队投影。单个用户授权继续使用技能仓库直接协作者。
最终权限按所有授权来源取最高值。

Q12 不做存量迁移。初始化会清理权限相关数据，保留组织、成员、技能和发布记录。
Q27 不再纳入本次范围。

## Alternatives considered

1. **继续把 permission 放在自定义团队上**：实现改动最小，但无法按技能区分权限，
   直接违反产品需求。
2. **为每个技能复制一套用户可见团队**：能够表达权限，但团队数量和用户心智负担
   随技能增长，且团队成员管理会产生多个不一致来源。
3. **在 ESL 数据库中保存权限但不投影内部团队**：可以减少 Git Backend 团队数量，
   但无法利用 Git Backend 原生团队权限计算，且成员同步与仓库访问容易分叉。

选择内部三团队投影，是为了把逻辑团队的成员管理与技能授权的权限选择解耦，同时
保持 Git Backend 的权限模型简单、可重建。

## Consequences

- 团队创建和编辑 API 不再接受固定 permission。
- 技能权限 API 必须支持按技能设置团队 permission。
- 团队删除需要跨技能清理授权和三个内部团队。
- 权限初始化是破坏性重置，不提供旧数据迁移。
- 内部团队命名、重建和清理必须是幂等操作。
