# ESL 用户工作流

本文件面向“我想完成什么”的用户场景；具体命令、参数和协议细节分别见 `setup.md`、`consumer.md`、`author.md` 与 `agent-interaction.md`。

## 统一执行模型

每个任务都按以下顺序推进：

1. **明确结果**：用户最终想得到什么，而不是先猜命令。
2. **判断来源**：远端技能、本地目录、已安装技能，还是 `@builtin/*` 内置技能。
3. **按需体检**：只检查当前任务需要的 CLI、Server、登录、Git 和目录条件。
4. **先读后写**：先做只读检查；涉及本地写入、远端写入或对外可见时，先回显完整命令并确认。
5. **执行一小步**：不要一次铺开整条命令清单。
6. **验证结果**：用成功判据确认，而不是仅凭命令退出成功。
7. **给出下一步**：任务完成、等待用户选择或进入下一个阶段。

每一步对用户说明：**当前阶段、会改变什么、成功判据、失败后的下一步**。

## 环境按任务检查

| 目标 | 最小检查 |
|---|---|
| 查看本地技能 | `esl --version`；无需 Server、登录或 Git |
| 安装 `@builtin/esl-operator` | `esl --version`；不访问 Server，不需要登录或 Git |
| 搜索/查看远端技能 | CLI、Server；私有结果需要登录 |
| 试用远端技能 | CLI、Server、访问权限；不把试用误当安装 |
| 安装/更新远端技能 | CLI、Server、登录、Git；还要确认项目/全局与工具 |
| 本地校验 | CLI、有效技能目录；通常无需 Server、登录或 Git |
| 上传/发布 | CLI、Server、登录、Git、源码状态与权限 |
| 克隆源码 | CLI、Server、登录、Git |

普通 CLI 用户不需要 Docker；只有明确要运行本地 ESL Server 时才读取本地开发文档。

## 场景一：发现并试用技能

### 目标
根据自然语言目标找到合适的已发布技能，先比较，再决定试用或安装。

### 最短路径

```text
描述要解决的问题 → 搜索 → 查看详情 → 试用（可选）→ 选择安装或停止
```

先问一个必要问题：**你想让技能帮你完成什么任务？** 如果目标已明确，不重复询问。

- 使用 `esl skill search --json` 获取候选，不直接安装。
- 用名称、显示名、描述、关键词、版本和可见性比较候选。
- 用 `esl skill info` 复核选中的身份和版本。
- 只想了解 Prompt 或验证行为时用 `esl skill use`；它不写入 Store、不创建 Tool Link。

**完成标准**：用户已经选定明确的 `@scope/name`、版本策略和下一步（试用、安装或停止）。没有合适结果时，不要随意安装相似技能；说明搜索范围、权限或 Server 可能导致的限制。

## 场景二：安装并接入工具

### 目标
把已选技能安装到当前项目或全局 Store，并按用户选择接入 AI 工具。

### 执行前必须确认

- 技能身份和版本；
- 当前项目级还是全局级；
- 目标工具（如 Codex、Claude Code、Cursor、Trae）；
- 普通安装还是本地 Skill Source Link；
- 是否允许拉取发布依赖。

不要把“安装到我这里”默认解释成全局安装。`Tool Link` 是已安装技能到具体 AI 工具的链接，不等于安装本身；`Skill Source Link` 是开发态源码链接，也不等于 Tool Link。

### 最短路径

```text
确认范围与工具 → 执行 install → 处理 Agent Interaction 工具选择 → list --json 验证
```

**完成标准**：技能、版本、安装范围、安装模式和目标工具均符合预期；本地 Store 有记录，目标 Tool Link 正常，项目清单/锁文件没有意外变化。

## 场景三：检查、更新、修复或卸载

### 最短路径

```text
list --json 查看现状 → 明确影响范围 → update/link/unlink/uninstall → 再次 list --json 验证
```

先区分：用户要更新内容、修复工具链接、解除源码链接，还是删除安装。卸载前说明项目/全局范围和依赖影响；修复链接优先使用 CLI 的专用 update/link 能力，不手工复制工具目录。

**完成标准**：本地状态与用户目标一致，Tool Link 和项目锁文件没有未预期的残留或删除。

## 场景四：从零创建或接入已有技能

### 从零创建

```text
目标与边界 → source init → 编写 SKILL.md/references → source validate → skill use 试跑 → 决定是否上传
```

初始化前优先收集：技能名称、解决的问题、目标用户、输入、输出、边界、最小示例。不要把 `source validate` 当作内容质量审查：它验证结构，不保证技能描述清晰或行为有效。

### 接入已有目录

```text
识别目录 → source validate → 检查 release.json/托管状态 → 本地试跑 → 决定 upload 或仅本地使用
```

已有 `SKILL.md` 不代表已经托管或可以发布；先检查源状态和身份。若用户只是想本地使用，可以停在校验/安装，不要擅自上传。

**完成标准**：本地技能结构合法，用户能用最小案例验证行为，并明确选择“仅本地使用”或“进入上传流程”。

## 场景五：二次开发已有技能

先确认用户要的是 Prompt 试用还是源码修改：

- 试用：`esl skill use`；
- 获取源码：`esl source clone`；
- 修改后：`source validate` → `source status` → 按权限决定 upload/publish。

不要把已安装副本当成可安全发布的源码，也不要通过修改 `release.json.name` 伪造跨命名空间归属。

## 场景六：上传源码与发布版本

这两个动作必须明确区分：

```text
本地草稿
  └─ source validate
       └─ source upload       # 登记/同步维护中的源码，不等于可安装发布
            └─ release version # 准备不可变版本
                 └─ release publish # 让版本进入可安装 Registry
```

### 上传前检查

- 不是 `@builtin/*`；
- `source validate` 成功；
- namespace、短名、display name 和描述正确；
- 当前账号有权限；
- Git 工作区、提交和远端状态符合预期；
- 不含密码、token、密钥等敏感信息。

### 发布前检查

- 源码已托管并同步；
- 版本号符合预期且未占用；
- 发布依赖已确认；
- 可见性和共享范围已确认；
- 用户明确知道发布会影响其他用户。

发布完成后用 `skill info` 或搜索确认 Registry 已出现正确版本；如果只是上传成功，不要宣称“已发布”。

**完成标准**：源码同步成功、Release 创建成功、Publish 成功，并能在 Registry 中查询到对应版本；任一阶段失败都停在该阶段，不跳过检查强行继续。

## 场景七：共享与权限

用户说“分享给公司”时，先确认是组织全员、团队还是指定成员，以及只读、读写还是管理权限。使用 `skill share` 前说明这是远端权限变更；完成后复核目标范围。不要猜组织名或权限等级。

## 内置技能边界

`@builtin/esl-operator` 随 CLI 发布，从本地内置资源安装：不访问 Server、不需要登录或网络，也不可 `source upload`、`source clone`、`release version`、`release publish` 或 `source rename`。不要把它当普通远端技能。

## 任务完成报告

完成后用简短报告说明：

- 任务与技能身份；
- 版本；
- 项目级/全局级；
- Tool Link 或源码托管状态；
- 验证命令和结果；
- 可选的下一步。

如果用户只完成了体检、搜索、上传或版本准备，要准确报告当前阶段，不要提前宣称已安装或已发布。
