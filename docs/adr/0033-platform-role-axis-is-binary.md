# 平台角色恒为两个：组织治理是团队身份，不是角色

Status: accepted

平台的**全局**角色轴恰好两个取值——Super Administrator 与 Skill User——组织
内不存在角色。组织治理权由**组织管理团队**（即该 Gitea Organization 的
Owners 团队）的成员身份承载：进入该团队即持有该组织最高管理权（管理成员、
团队与组织设置，可见并管理本组织名下全部技能），它是一项**团队身份**，不是
平台给某人贴的角色标签。这修订 ADR-0032 中把「组织管理员」当作角色的表述，
并废止管理后台的第三类视角：`/admin/org/` 视角并入个人控制台。

## 背景与动因

1. ADR-0032 的代码落地里，`org-admin` 从来不是服务端角色——它是**登录时算出来
   的投影**：`POST /api/console/login` 对该用户在**任意**组织中是 Owners 成员
   就返回 `role: 'org-admin'`（`packages/server/src/routes/auth.ts:66-70`），
   服务端每个请求再按 Owners 成员身份复检（`org-console.ts` 的
   `requireOrgAdministrator`、`skills.ts` 的 `isOrgAdministrator`）。也就是说
   "组织管理员"在权限模型里早就是团队身份，只在术语表与 UI 上冒充角色。
2. 冒充角色的代价是真实的：`org-admin` 是 `some()` 全组织的结果，一旦在任一
   组织是治理者，整个后台就切到 org-admin 布局；而"当前在哪个组织"由客户端
   取**第一个** org-admin 组织推断（`LoginView.vue:78`），全站没有组织切换器。
   用户属于两个组织时，后台只能治理其中一个——角色是全局的，治理是分资源的，
   这个错配正是该 bug 的根因。
3. 角色应当是可枚举、平台级的；权限应当是资源级、通过团队授予的。二分角色轴
   让这两件事各归其位，也让"超管/普通用户"成为一句没有例外的真话。

## Considered Options

- **保留 `org-admin` 作为第三个平台角色**：与现状一致，且 Gitea 事实上允许
  "某组织的 owner、另一组织的普通成员"。但角色是全局单值，无法表达"在 A 是
  治理者、在 B 不是"，只能退化成现在的 `some()` 近似——弃。
- **把组织治理权收归组织创建者**：治理权与团队成员身份脱钩，创建者离开后组织
  无人可管；且与 Gitea Owners 机制正面冲突——弃。
- **让任何组织成员都可治理**：常设团队退化为纯技能授权载体，"成员"与"治理者"
  不再可分，撤销治理权只能靠移除成员（连带丢技能授权）——弃。

## Consequences

- `CONTEXT.md` 新增 **平台角色 (Platform Role)** 与 **组织管理团队 (Org Management
  Team)** 两个词条，删除 **Organization Admin** 词条；`Organization`、`Organization
  Team`、`技能可见性`、`技能管理页面`、`管理后台`、`组织注册申请` 等词条中
  "组织管理员"的指代一律改为组织管理团队成员。
- 管理后台从三类视角收为两类：Super Administrator 控制台与个人控制台。原
  `/admin/org/*` 的成员、团队、技能管理并入个人控制台，治理入口只对组织管理
  团队成员渲染（其余成员看到该组织时是只读的）。
- 四个常设团队维持现状自动生成（三档团队 + Owners/组织管理团队），自定义团队
  保留；成员加入组织时自动加入前三个常设团队。
- 角色枚举在 Web 侧从 `'super' | 'org-admin' | 'member'` 收为两项；服务端
  `OrganizationMembership.role` 的 `org-admin` 语义改为"是本组织组织管理团队
  成员"，且必须**按组织**判定，不再被提升为全局角色。
### 组织管理团队的成员互管

- 组织管理团队成员**可以互相移除**：不能移除自己，且移除后团队必须至少保留
  一名成员。这取代了代码里"ESL 不得将任何人移出 Owners"的硬禁止。
- **超管兜底 = 不经成员身份行使同款能力**，而不是破例：ESL Platform Administrator
  不属于任何组织（也就无法走组织侧路由），因此单开 `/api/admin/orgs/:orgName/members`
  给出查看与移除能力；"至少保留一名成员"对超管同样成立——真去掉了最后一名
  管理者的组织是**无主组织**，谁也治不了它。确实无人可用的组织走整体删除
  （超管路径已具备），而不是留下一个谁都进不去的组织。
- 推论：单管理者组织的唯一出路是删除，这条留给后续的"指定新管理者"补足。
- 理由是治理权的对称性与可退出性：禁止移除成员会让创建者成为不可移除的主子，
  一旦其离职或失联，组织只能靠超管兜底救；"至少留一人"保证组织不会变成无主
  资产。
- 组织管理团队**不设独立术语**指代"治理者的人"——治理者就是该团队成员，
  术语表用「组织管理团队」承载这一身份（原「Organization Admin」词条删除）。

### Super Administrator 不参与组织

- Super Administrator 只有 Super Administrator 控制台：不属于任何 Organization、
  不持有个人控制台、不以个人命名空间发布技能。组织的初始化仍需保证站点管理员
  **不在**该组织的 Owners 团队内（维持 `org-init` 的现有行为）。
- 理由是裁判身份不该进入比赛：平台管理员若能提交组织申请并由自己审批、能创建
  技能并参与组织内权限博弈，平台治理与成员治理就不可分离。需要技能作者身份的
  平台管理者，应当注册一个普通账号。
