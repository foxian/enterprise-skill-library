# 公开产品仓库与私有实例部署边界

Status: accepted

ESL 的开源代码可以被维护者自己的企业技能网站使用，但网站的域名、生产配置、
品牌内容和运营凭据不应随代码公开。需要明确产品层与实例层的所有权、同步方式和
升级边界。

## 决策

- 公开仓库 `enterprise-skill-library` 维护可复用的产品代码、通用 Docker/局域网
  部署能力和公开文档。默认配置不绑定任何域名：nginx 是 `default_server`，
  localhost/IP 开箱即用；`.env` 只有通用模板。
- 实例配置通过 `.gitignore` 管理的本地文件注入：`nginx-conf.d/` 中的自定义
  server 块挂载到容器 `/etc/nginx/conf.d`；TLS、Tunnel 配置同理。
  需要版本管理和审阅时，再为单个实例维护独立的私有部署仓库，保存真实域名、DNS、
  TLS、反向代理、Tunnel、环境变量、密钥引用、品牌资源、网站内容和部署流水线。
- 私有实例通过 Git tag、GitHub Release、npm 包或不可变 Docker 镜像依赖公开产品，
  必须锁定明确版本或 digest，不直接跟踪 `main`。
- 私有仓库可以保存网站 Markdown/JSON 内容并通过 Git 审阅、回滚和同步；内容变更
  不要求修改 ESL 核心代码。
- 通用能力回馈公开仓库；只属于单个实例的能力留在私有仓库，并记录对应的上游版本。
- 任何真实凭据、域名证书、DNS API Token、Tunnel Token、数据库密码和生产服务器
  地址都不得进入公开仓库或公开构建日志。
- 推荐升级流程：公开仓库发布带 changelog 的版本和镜像 → 私有仓库提交依赖版本
  变更并在测试环境构建、迁移和验证 → 验证通过后部署生产，保留旧版本作为回滚点。

## 考虑过的方案

- **把真实实例配置直接放入公开仓库**：会把某个实例的运维责任、隐私和生命周期
  错误地绑定到所有使用者；改为公开仓库仅提供占位示例和部署者注入配置。
- **让私有仓库 fork 整个公开仓库并长期维护**：会形成难以同步的私有分叉，升级
  成本随时间累积；改为私有仓库通过版本依赖消费公开产品，不复制代码。
- **把网站内容和品牌资源作为 ESL 核心的一部分**：会让内容发布与产品版本强耦合，
  每次文案修改都要重新发版；改为内容作为实例层资产独立管理、独立发布。

## 后果

- 公开代码与私有实例可以独立发布，真实域名不会成为开源项目的隐含契约。
- 私有实例需要维护上游版本和私有覆盖层，不能依赖未经验证的分支漂移。
- 产品层与实例层的缺陷修复责任清晰：通用修复进入公开仓库，实例专属问题由私有仓库
  负责。
