# 技能级团队权限模型设计

**日期：** 2026-09-15  
**状态：** 已确认

## 目标

让同一个自定义团队可以在不同技能上拥有不同权限，同时保留私有、全组织可读、
全组织可读写、全组织可管理四种技能共享状态，并支持单个用户的逐技能授权。

## 领域模型

### 逻辑团队

自定义团队是 ESL 层的逻辑团队。逻辑团队只表达成员集合和稳定身份，不再携带
固定的 Read、Write 或 Manage 技能权限。

每个逻辑团队在 Git Backend 中投影为三个内部权限团队：

```text
<stable-team-key>-read
<stable-team-key>-write
<stable-team-key>-manage
```

内部团队只用于实现权限，不在 ESL 用户界面中展示。逻辑团队成员同步到三个内部
团队，以便同一团队可以在不同技能中被挂载到不同权限档位。

### 技能团队授权

每个技能对每个逻辑团队最多有一个授权档位：

```text
none | read | write | manage
```

技能 A 可以把 `frontend` 授权为 Read，技能 B 可以把同一个 `frontend` 授权为
Write。切换档位时，撤销该技能上的旧内部团队挂载，再挂载新内部团队。

### 个人授权

单个用户继续使用技能仓库上的直接协作者授权，可逐技能设置 Read、Write 或
Manage。最终有效权限取所有来源的最高值：

```text
None < Read < Write < Manage
```

来源包括全组织共享、逻辑团队授权、个人直接授权、技能 Maintainer 和组织治理
结构权限。

### 全组织共享

全组织共享继续使用三个固定组织团队：

```text
all-readers
all-writers
all-managers
```

私有表示没有默认全组织授权，不会阻止精细的团队或个人授权。切换全组织共享
只改变固定组织团队在当前技能仓库上的挂载，不删除自定义团队或个人授权。

### 生命周期

- 创建和编辑逻辑团队只接受 `name`、`display_name`，不接受固定 `permission`。
- 重命名不改变逻辑团队 ID 或已有技能授权。
- 成员增删同步三个内部权限团队。
- 删除逻辑团队时撤销全部技能团队授权、删除三个内部团队，再删除逻辑团队记录；
  操作必须可恢复或可重试。
- 若内部团队被 Git Backend 误删，ESL 可按逻辑团队记录重建并恢复成员和挂载。
- 新成员加入组织时只进入固定组织只读、读写团队，不自动进入自定义团队。

## 数据初始化

Q12 不做存量兼容迁移。Q27 从需求范围中删除。

初始化清理全部权限相关数据：

- 自定义逻辑团队及成员关系；
- 三个内部权限团队；
- 技能仓库团队挂载；
- 技能仓库个人协作者授权；
- 全组织共享挂载；
- ESL 数据库中的团队权限和授权记录；
- 相关 seed 与测试权限 fixture。

初始化保留组织、成员账号、技能、技能源码和技能发布记录，并重建三个固定组织
团队及组织成员关系。不恢复旧自定义团队或旧技能授权。

## API

团队 API：

```http
POST /api/orgs/:org/teams
{ "name": "...", "display_name": "..." }

PATCH /api/orgs/:org/teams/:id
{ "name": "...", "display_name": "..." }
```

技能权限 API：

```json
{ "action": "set_team", "team_id": 7, "permission": "read" }
{ "action": "remove_team", "team_id": 7 }
{ "action": "add_member", "username": "alice", "permission": "write" }
```

## 非目标

- 不改变 Owners 团队的组织治理语义。
- 不把固定组织团队拆成三组逻辑团队。
- 不恢复 Q27。
- 不为旧权限数据提供迁移兼容层。

## 验收标准

1. 同一逻辑团队可在两个技能上分别获得 Read 和 Write。
2. 团队成员变更会同步到三个内部权限团队。
3. 修改一个技能的团队档位不会影响其他技能。
4. 删除逻辑团队会清理所有技能挂载和内部团队。
5. 用户直接授权、团队授权和全组织授权取最高权限。
6. 初始化清理权限数据但保留技能和发布记录。
7. 创建逻辑团队不再需要 `permission`。
