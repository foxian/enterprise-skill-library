# 技能锻造坊（Skill Forge）

用于创建新技能并迭代改进它们的技能。

从宏观上看，创建一个技能的过程大致如下：

- 确定你希望这个技能做什么，以及大致该怎么做
- 新建技能时先确定并确认名称，再写一份技能草稿
- 编写几个测试提示词，让加载了该技能的 AI 助手在上面跑一跑
- 帮助用户从定性和定量两个角度评估结果
  - 运行在后台进行的同时，如果还没有定量评测，就先起草一些（如果已有，你可以直接使用，或者觉得需要调整就修改）。然后向用户解释这些评测（如果已经存在，就解释已有的那些）
  - 用 `eval-viewer/generate_review.py` 脚本把结果展示给用户查看，同时也让他们看到定量指标
- 根据用户对结果评估的反馈重写技能（另外，如果定量基准测试暴露出明显的缺陷，也要一并修复）
- 如此重复，直到你满意为止
- 扩大测试集，更大规模地再试一次

使用这个技能时，你的工作是判断用户当前处于这个流程的哪个阶段，然后介入并帮助他们推进这些阶段。比如，他们可能会说"我想做一个 X 技能"。你可以帮助缩小他们的意图范围、写草稿、写测试用例、弄清他们想怎么评估、运行所有提示词，然后重复。

另一方面，他们可能已经有了技能草稿。这种情况下你可以直接进入评估/迭代环节。

当然，你应该始终保持灵活——如果用户说"我不需要跑一堆评估，就凭感觉跟我来"，那你照做就行。

技能完成后（同样，顺序是灵活的），你还可以运行技能描述优化器——我们有一个单独的脚本——来优化技能的触发效果。

明白？明白。

## 与用户沟通

技能锻造坊可能被各种熟悉程度的人使用，包括对编程术语一窍不通的人。如果你没听说过（说起来你怎么可能听说过呢，这也是最近才开始的趋势），现在有一种风潮：AI 助手的强大能力激励着水管工打开终端、父母和祖父母去谷歌"怎么安装 npm"。另一方面，大多数用户可能还是相当懂电脑的。

所以请注意上下文线索，来决定该如何措辞！在默认情况下，给你一些参考：

- "evaluation（评估）"和"benchmark（基准测试）"算是边界情况，但可以使用
- 对于"JSON"和"assertion（断言）"，在不加解释就使用之前，你需要看到用户有明确的信号表明他们懂这些东西

如果有疑问，简单解释一下术语是没问题的；如果不确定用户是否理解，尽管用简短的定义来澄清。

## 创建技能

### 捕获意图

首先理解用户的意图。当前对话中可能已经包含用户想要固化的工作流（比如他们说"把这个变成一个技能"）。如果是这样，先从对话历史中提取答案——用到的工具、步骤顺序、用户做过的修正、观察到的输入/输出格式。用户可能需要补充细节，并且应该在进入下一步之前予以确认。

1. 这个技能应该让 AI 助手能做什么？
2. 这个技能应该在什么时候触发？（什么样的用户措辞/情境）
3. 期望的输出格式是什么？
4. 是否要设置测试用例来验证技能有效？输出可客观验证的技能（文件转换、数据提取、代码生成、固定工作流步骤）适合有测试用例。输出主观的技能（写作风格、艺术）通常不需要。根据技能类型建议合适的默认选项，但让用户决定。

### 访谈与调研

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。在把这些敲定之前，先别急着写测试提示词。

检查可用的 MCP——如果对调研有用（搜索文档、查找类似技能、查最佳实践），有子代理的话就通过子代理并行调研，否则就内联调研。带着充分的背景信息来做准备，减少用户的负担。

### 命名与确认（仅新建技能）

需求范围明确后、创建技能目录或编写技能文件之前，先阅读 `references/authoring.md` 的“命名规范”，再确定技能标识符。更新已有技能跳过此环节，按“更新现有技能”一节保留原名。

- **用户已明确指定标识符**：检查名称格式及可检查的目标目录冲突；无问题直接沿用，不展示候选、不重复确认。用户只提供中文标题、尚未明确可用标识符时，以该标题为依据拟定候选。
- **用户未指定标识符**：默认提供 3 个有实际区别的候选名，每个附一句命名理由；标记一个推荐项，并说明它相较其他候选的优势。依据核心能力、需求范围及已有技能库的命名风格拟名，不用调换单词或堆砌近义词凑数。
- **邀请用户决定**：用户可以选择候选、给出自己的名称，或提出偏好要求重新拟名。拒绝全部候选时，根据反馈调整，不擅自采用原推荐项。未获得名称选择或明确授权前，不创建新技能目录、不写入技能文件。
- **用户明确授权自行决定**（如“你决定”“不用问我”）：可以采用推荐名继续创建，简要说明采用的名称及理由，无需暂停等待。
- **自定义名称不符合约束**：解释具体问题并提出合法替代写法，等待用户确认，不静默改名。名称存在目标目录冲突时，不覆盖、不自动追加后缀；说明冲突，请用户选择其他名称或明确改为更新已有技能。无法检查目标目录时，说明尚未确认是否冲突，不声称已完成查重。

名称确定后，统一使用同一标识符作为技能目录名、SKILL.md frontmatter 的 `name` 和打包名，再进入编写步骤。

### 输出位置与路径报告（仅新建技能）

- **默认位置**：新建技能默认放在当前工作区的 `skills/<skill-name>/` 目录下。例如，标识符为 `pdf-processing` 时，默认目录为 `<工作区>/skills/pdf-processing/`。创建前检查目标目录是否存在；存在时不覆盖、不自动追加后缀，按“命名与确认”流程请用户另选名称或明确改为更新已有技能。
- **用户指定位置优先**：用户明确指定技能根目录时，使用用户指定的位置；仍须使用已确认的同一标识符作为目录名、frontmatter `name` 和打包名，并在创建前报告将使用的路径。
- **无法确定工作区或目标位置**：不要猜测并直接写入。先说明无法确定目标路径，请用户提供位置，或明确授权使用当前工作目录下的 `skills/` 目录。
- **完成时报告绝对路径**：创建完成后报告技能目录的绝对路径；如果生成 `.skill` 包，也报告包文件的绝对路径。路径不存在或尚未实际生成时，不得声称已生成。


### 编写 SKILL.md

根据用户访谈，填写这些组成部分：

- **name**：技能标识符
- **description**：做什么 + 何时用，两要素缺一不可；始终用第三人称写（描述会被注入系统提示词，视角不一致会损害触发）。这是主要的触发机制——既要写技能做什么，也要写使用它的具体情境。所有"何时使用"的信息都放这里，不放正文。注意：目前模型普遍倾向于"触发不足"——在技能本该有用时不使用它。为了对抗这一点，请把技能描述写得稍微"强势"一点。比如，不要写"如何构建一个简单快速的仪表盘来展示内部业务数据。"，你可以写"如何构建一个简单快速的仪表盘来展示内部业务数据。只要用户提到仪表盘、数据可视化、内部指标，或想展示任何种类的公司数据，务必使用本技能，即使他们没有明确要求'仪表盘'。"
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

完整的写作工艺（精简原则、自由度校准、命名与 description 规范、工作流模式、脚本编写规范、发布前检查清单）见 `references/authoring.md`——起草技能正文前先通读一遍；技能包含 scripts/ 时，其中"脚本编写规范"一节必读。技能涉及项目文件、输出目录或脚本路径时，读 `references/paths.md`。

#### 技能的解剖结构

```
skill-name/
├── SKILL.md（必需）
│   ├── YAML frontmatter（name、description 必需）
│   └── Markdown 指令
└── 打包资源（可选）
    ├── scripts/    - 用于确定性/重复性任务的可执行代码
    ├── references/ - 按需加载进上下文的文档
    └── assets/     - 用于输出的文件（模板、图标、字体）
```

#### 渐进式披露

技能使用三级加载系统：
1. **元数据**（name + description）- 始终在上下文中（约 100 词）
2. **SKILL.md 正文** - 技能触发时进入上下文（理想情况下 <500 行）
3. **打包资源** - 按需加载（数量不限，脚本可以不加载就执行）

这些字数是大致参考，必要时你可以写得更长。

**关键模式：**
- 保持 SKILL.md 在 500 行以内；如果接近这个限制，增加一层层级结构，并清晰指明使用该技能的模型下一步该去哪里跟进。
- 在 SKILL.md 中清晰引用参考文件，并说明何时阅读它们
- 对于大型参考文件（>300 行），附上目录

**领域组织**：当一个技能支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md（工作流 + 选择）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
模型只读取相关的参考文件。

#### 意料之外原则

这本是不言自明的，但技能绝不能包含恶意软件、漏洞利用代码或任何可能危及系统安全的内容。如果如实描述，技能的内容不应让用户在意图上感到意外。不要配合那些创建误导性技能、或旨在促进未经授权访问、数据窃取及其他恶意活动的请求。不过像"扮演 XYZ 角色"这类请求是可以的。

#### 写作模式

指令中优先使用祈使语气。

**定义输出格式** - 你可以这样写：
```markdown
## 报告结构
务必使用这个精确模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式** - 包含示例很有用。你可以这样组织（但如果示例中出现"输入"和"输出"字样，你可能需要稍微变通一下）：
```markdown
## 提交信息格式
**示例 1：**
输入：Added user authentication with JWT tokens
输出：feat(auth): implement JWT-based authentication
```

### 写作风格

默认假设：模型已经相当聪明——只写模型不知道的内容，对每一段自问"模型真的需要这个解释吗？这段话值它的 token 成本吗？"。

试着向模型解释事情为什么重要，而不是堆砌生硬死板的 MUST。运用心智理论（theory of mind），尽量让技能具有通用性，而不是狭隘地绑定到特定示例。先写一版草稿，然后换上全新的眼光审视并改进它。

### 测试用例

写完技能草稿后，想出 2-3 个真实的测试提示词——真实用户真正会说的话。和用户分享它们：[不必用这个确切的说法] "这里有几个我想试的测试用例。这些看起来对吗，还是你想再加几个？"然后运行它们。

把测试用例保存到 `evals/evals.json`。先别写断言——只写提示词。你可以在下一步运行进行期间起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整 schema（包括你稍后要添加的 `assertions` 字段）见 `references/schemas.md`。

## 运行和评估测试用例

这一节是一个连续的过程——不要半途而废。不要使用 `/skill-test` 或任何其他测试技能。

把结果放在技能目录同级的 `<skill-name>-workspace/` 中。在 workspace 内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），每次迭代内每个测试用例一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些——用到时再创建目录。

### 第 1 步：在同一个回合中启动所有运行（带技能 AND 基线）

对每个测试用例，在同一回合中启动两个子代理——一个带技能，一个不带。这点很重要：不要先启动带技能的运行，之后再回来跑基线。一次性启动所有任务，这样它们差不多同时完成。

**带技能的运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行**（提示词相同，但基线取决于上下文）：
- **创建新技能**：完全不用技能。相同的提示词，不带技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。编辑之前，先对技能做快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后让基线子代理指向这个快照。保存到 `old_skill/outputs/`。

为每个测试用例写一个 `eval_metadata.json`（断言暂时可以为空）。根据每个 eval 测试的内容给它起一个描述性的名字——不要只叫 "eval-0"。目录也用这个名字。如果这一轮迭代使用了新的或修改过的 eval 提示词，就为每个新的 eval 目录创建这些文件——不要假设它们会从上一轮迭代继承。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：运行进行期间，起草断言

不要只是等着运行结束——你可以充分利用这段时间。为每个测试用例起草定量断言并向用户解释。如果 `evals/evals.json` 中已有断言，就审阅它们并解释它们检查什么。

好的断言是可客观验证的，并且有描述性的名字——它们在基准查看器中应该一目了然，别人扫一眼结果就能立刻明白每条断言检查什么。主观性的技能（写作风格、设计质量）更适合定性评估——不要把断言强加到需要人类判断的事情上。

断言起草完成后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。还要向用户解释他们将在查看器中看到什么——既有定性输出，也有定量基准。

### 第 3 步：运行完成时，捕获计时数据

每个子代理任务完成时，你会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即把这个数据保存到运行目录下的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这个数据的唯一机会——它通过任务通知传进来，不会被持久化到其他地方。收到每条通知就立即处理，不要试图攒起来批量处理。

### 第 4 步：评分、汇总并启动查看器

所有运行完成后：

1. **给每次运行评分** —— 启动一个评分子代理（或内联评分），让它读取 `agents/grader.md` 并根据输出评估每条断言。把结果保存到每次运行目录下的 `grading.json`。grading.json 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以编程检查的断言，写脚本来运行，而不是靠肉眼——脚本更快、更可靠，而且可以跨迭代复用。

2. **汇总成基准** —— 从 skill-forge 目录运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，包含每种配置的 pass_rate、时间和 token，带均值 ± 标准差和差值。如果手动构建 benchmark.json，查看器期望的确切 schema 见 `references/schemas.md`。
   每个 with_skill 版本放在其基线对应项之前。

3. **做一次分析** —— 阅读基准数据，找出汇总统计可能掩盖的模式。看 `agents/analyzer.md`（"分析基准结果"一节）了解该找什么——比如无论用不用技能总是通过的断言（无区分度）、高方差的 eval（可能不稳定）、时间/token 的权衡。

4. **启动查看器**，同时展示定性输出和定量数据：
   ```bash
   python <skill-forge-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json
   ```
   脚本会启动一个本地服务器并自动打开浏览器；用完后在终端按 Ctrl+C（或终止该进程）停止。第 2 轮迭代及以后，还要传 `--previous-workspace <workspace>/iteration-<N-1>`。

   **无头环境（无显示器/浏览器，或 `webbrowser.open()` 不可用）：** 使用 `--static <output_path>` 写出一个独立的 HTML 文件，而不是启动服务器；把该文件交付给用户（文件链接或下载路径），让他们在本地浏览器打开。当用户点击"Submit All Reviews"时，反馈会作为 `feedback.json` 文件下载。拿到后把 `feedback.json` 放到 workspace 目录，供下一轮迭代读取。

   注意：请使用 generate_review.py 来创建查看器；不需要自己写 HTML。

5. **告诉用户**，类似这样说："我已经在你的浏览器中打开了结果。有两个标签页——'Outputs' 让你可以逐个查看测试用例并留下反馈，'Benchmark' 显示定量对比。完成后回到这里告诉我。"

### 用户在查看器中看到什么

"Outputs" 标签页一次显示一个测试用例：
- **Prompt**：给出的任务
- **Output**：技能产出的文件，尽可能内联渲染
- **Previous Output**（第 2 轮起）：折叠区域，显示上一轮迭代的输出
- **Formal Grades**（如果运行了评分）：折叠区域，显示断言的通过/失败
- **Feedback**：一个输入框，输入时自动保存
- **Previous Feedback**（第 2 轮起）：他们上次的评论，显示在输入框下方

"Benchmark" 标签页显示统计摘要：每种配置的通过率、耗时和 token 用量，带每个 eval 的细分和分析观察。

导航通过上一个/下一个按钮或方向键。完成后，他们点击"Submit All Reviews"，把所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们完成了，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈意味着用户认为没问题。把改进重点放在用户有具体意见的测试用例上。

用完后停止查看器服务器：在运行它的终端按 Ctrl+C，或者终止该 Python 进程。

## 改进技能

这是循环的核心。你已经运行了测试用例，用户已经审阅了结果，现在你需要根据他们的反馈让技能变得更好。

### 如何思考改进

1. **从反馈中泛化。** 这里发生的大局是：我们试图创建能被使用上百万次（也许是真的上百万，甚至更多，谁知道呢）的技能，适配各种不同的提示词。而你和用户在这里只反复迭代少数几个示例，因为这样推进更快。用户对这些示例了如指掌，评估新输出对他们来说很快。但如果你和用户共同开发的技能只对那几个示例有效，那它就是没用的。与其做些琐碎的过拟合式改动，或者令人窒息的严苛 MUST，如果碰到某个顽固问题，你可以尝试换个方向，使用不同的隐喻，或者推荐不同的工作模式。尝试的成本相对较低，也许你会撞上好点子。

2. **保持提示词精简。** 删掉不起作用的内容。务必阅读完整的执行记录（transcript），而不只是最终输出——如果看起来技能在让模型浪费大量时间做无用功，你可以试着删掉技能中导致这种行为的部分，看看会发生什么。

3. **解释原因。** 努力解释你要求模型做的每件事背后的**原因**。如今的 LLM 很*聪明*。它们有良好的心智理论，在好的框架下能超越死板的指令，真正把事情做成。即使用户的反馈很简短或带着情绪，也要试着真正理解任务本身、理解用户为什么写他们写的内容、理解他们实际写了什么，然后把这种理解传递进指令里。如果你发现自己在写全大写的 ALWAYS 或 NEVER，或者使用超级僵化的结构，那是个黄色警示——如果可能的话，换个说法并解释理由，让模型理解你要求的事情为什么重要。这是更人性化、更强大、也更有效的方法。

4. **寻找测试用例间的重复工作。** 阅读测试运行的执行记录，注意子代理们是不是都各自写了类似的辅助脚本，或者对同一件事采用了相同的多步方法。如果 3 个测试用例都让子代理写了一个 `create_docx.py` 或 `build_chart.py`，这是技能应该打包该脚本的强烈信号。写一次，放进 `scripts/`，然后让技能使用它。这能省去以后每次调用都重新造轮子。

这个任务相当重要（我们在这里试图创造每年数十亿美元的经济价值！），你的思考时间不是瓶颈；慢慢来，好好琢磨。我建议先写一版修改草稿，然后用全新的眼光审视并改进。真的尽你所能站到用户的角度，理解他们想要什么、需要什么。

### 迭代循环

改进技能之后：

1. 把你的改进应用到技能上
2. 把所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。如果你在创建新技能，基线始终是 `without_skill`（无技能）——这在各轮迭代中保持不变。如果你在改进现有技能，自行判断什么作为基线合理：用户最初带来的原始版本，还是上一轮迭代。
3. 启动审阅器，`--previous-workspace` 指向上一轮迭代
4. 等待用户审阅并告诉你他们完成了
5. 读取新反馈，再次改进，重复

继续，直到：
- 用户说他们满意了
- 反馈全是空的（一切看起来都不错）
- 你无法取得有意义的进展

## 进阶：盲测对比

当你想更严格地对比技能的两个版本时（比如用户问"新版本真的更好吗？"），有一个盲测对比系统。详情见 `agents/comparator.md` 和 `agents/analyzer.md`。基本思路是：把两个输出交给一个独立的代理，不告诉它哪个是哪个，让它评判质量。然后分析赢家为什么赢。

这是可选的，需要子代理，大多数用户用不到。人工审阅循环通常就够了。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定模型是否调用某技能的主要机制。创建或改进技能后，主动提出为更好的触发准确率而优化描述。

### 第 1 步：生成触发评测查询

创建 20 条评测查询——混合应该触发和不应该触发的。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实，是使用各类 AI 编程工具或对话式 AI 的用户真正会打出来的内容。不是抽象的请求，而是具体、明确、有足够细节的请求。比如：文件路径、关于用户工作或处境的个人背景、列名和值、公司名、URL。一点前因后果。有些可能是小写、带缩写、错别字或口语化的。混合不同的长度，关注边界情况而不是把它们做得一目了然（用户会有机会签字确认）。

差：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于**应该触发**的查询（8-10 条），考虑覆盖面。你要的是同一意图的不同措辞——有些正式，有些随意。包括用户没有明确说出技能名或文件类型但显然需要它的情况。再加入一些少见的用例，以及这个技能与另一个技能竞争但应该胜出的情况。

对于**不应该触发**的查询（8-10 条），最有价值的是那些"差一点"的——与技能共享关键词或概念但实际上需要别的东西的查询。想想相邻领域、天真的关键词匹配会触发但实际不该触发的歧义措辞，以及查询涉及技能所做之事但语境上更适合另一个工具的情况。

关键要避免的：不要让不该触发的查询显得明显无关。"写一个 fibonacci 函数"作为 PDF 技能的负例测试太简单了——它什么都没测试到。负例应该真正刁钻。

### 第 2 步：与用户审阅

使用 HTML 模板向用户展示评测集供审阅：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评测项的 JSON 数组（不加引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的描述
3. 写入系统临时目录（macOS/Linux 为 `/tmp/eval_review_<skill-name>.html`，Windows 为 `%TEMP%\eval_review_<skill-name>.html`）并用系统默认方式打开（macOS 用 `open`，Linux 用 `xdg-open`，Windows 用 `start`）；无头环境则把该 HTML 文件直接交付给用户
4. 用户可以编辑查询、切换 should-trigger、增删条目，然后点击 "Export Eval Set"
5. 文件会下载到用户的下载目录（通常是 `~/Downloads/eval_set.json`）——如果有多份（如 `eval_set (1).json`），检查下载文件夹中最新的一份

这一步很重要——糟糕的评测查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户："这会花一些时间——我会在后台运行优化循环，并定期查看进展。"

**前置条件：无头 AI 命令行。** 自动优化循环通过 subprocess 调用一个非交互式（无头）AI CLI 来批量跑触发测试和改写描述。默认后端是 Claude Code 的 `claude -p`。如果当前环境没有安装它，或你想使用其他工具的等价 CLI：

- 触发测试（`run_eval.py`）目前解析的是 Claude Code 的 `stream-json` 事件协议、并通过 `.claude/commands/` 注册临时技能，因此 `SKILL_AGENT_CLI` 指定的命令必须兼容这套协议；
- 描述改写（`improve_description.py`）只需要"提示词进、文本出"，任何等价的无头 CLI 都可通过环境变量替换：
  ```bash
  # 默认值：claude -p --output-format text
  export SKILL_AGENT_CLI="your-agent-cli --some-flags"
  ```
  （Windows PowerShell 用 `$env:SKILL_AGENT_CLI = "..."`。）自定义命令时请把模型选择直接写进命令参数中，脚本不会再追加 `--model`。

如果没有任何可用的无头 CLI，跳过自动优化循环，改为在对话中手动抽测触发情况并人工打磨描述。

把评测集保存到 workspace，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用你系统提示词中的模型 ID（驱动当前会话的那个），这样触发测试才能匹配用户实际的体验。该参数会以 `--model` 传给默认的 Claude Code 后端；使用自定义 `SKILL_AGENT_CLI` 时此参数被忽略。

运行期间，定期查看输出，向用户更新当前在第几轮迭代、分数如何。

这会自动处理完整的优化循环。它把评测集按 60% 训练、40% 留出测试拆分，评估当前描述（每条查询跑 3 次以获得可靠的触发率），然后调用模型根据失败情况提出改进。它会在训练集和测试集上分别重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，展示每轮迭代的结果，并返回包含 `best_description` 的 JSON——按测试分数而非训练分数选出，以避免过拟合。

### 技能触发的工作原理

理解触发机制有助于设计更好的评测查询。技能带着它们的 name + description 出现在模型的可用技能列表中，模型根据这个描述决定是否参考某个技能。需要了解的重要一点是：模型只有在无法自行轻松处理的任务上才会参考技能——像"读这个 PDF"这样简单一步到位的查询，即使描述完全匹配也可能不触发技能，因为模型用基础工具就能直接处理。复杂的、多步的或专业化的查询，只要描述匹配就能可靠地触发技能。

这意味着你的评测查询应该有足够的实质性，让模型确实能从参考技能中受益。像"读文件 X"这样的简单查询是糟糕的测试用例——无论描述质量如何它们都不会触发技能。

### 第 4 步：应用结果

从 JSON 输出中取出 `best_description`，更新技能的 SKILL.md frontmatter。向用户展示前后对比并报告分数。

## 按运行环境适配（不同 AI 工具通用）

本技能不绑定任何特定的 AI 工具。核心工作流（草稿 → 测试 → 审阅 → 改进 → 重复）在任何支持技能机制的工具中都一样，但不同工具提供的能力不同。**请按能力而非工具名来判断如何调整**——开工前先确认当前环境具备下面哪些能力。

### 能力 1：能否启动独立子代理（后台任务）

- **能**：主工作流完整可用——同一回合并行启动"带技能/基线"运行、评分子代理、盲测对比。如果遇到严重的超时问题，可以改为串行运行测试提示词。
- **不能**（如纯对话式界面）：
  - 对每个测试用例，自己读取技能的 SKILL.md 并按其指令完成测试提示词，一次一个。这不如独立子代理严格（技能是你写的，你又在运行它，上下文是完整的），但仍是有用的健全性检查，人工审阅步骤可以弥补。
  - 跳过基线运行和定量基准测试（它们依赖独立的对比执行），专注用户的定性反馈。
  - 盲测对比同样跳过。
  - 迭代循环照常：改进技能 → 重新运行测试 → 征求反馈。如果文件系统可用，仍然把结果组织到迭代目录中。

### 能力 2：能否打开浏览器 / 有无显示器

- **能**：正常运行 `generate_review.py`，它会启动本地服务器并打开浏览器；反馈由查看器自动保存到 workspace 的 `feedback.json`。
- **不能**（远程服务器、无头沙箱、虚拟机等）：
  - 用 `--static <output_path>` 生成独立 HTML 文件，把它交付给用户（文件链接/下载路径）在本地浏览器打开。
  - 查看器的 "Submit All Reviews" 会把 `feedback.json` 作为文件下载；拿到后把它放回 workspace 目录（可能需要先请求文件访问权限）。
  - 如果连 HTML 文件都无法交付，就完全跳过浏览器审阅器，直接在对话中逐个展示提示词和输出；用户需要查看的文件（如 .docx、.xlsx）保存到文件系统并告知路径。就地征求反馈："这些看起来怎么样？有什么想改的吗？"

**无论在哪种环境，跑完测试后都要先把结果摆到人类面前，再自己动手修订技能。** 优先使用 `generate_review.py` 生成查看器（无头就用 `--static`），不要自己写定制 HTML。这里要特别强调：在你自己评估输入之前，先生成 eval 查看器 *（GENERATE THE EVAL VIEWER BEFORE evaluating inputs yourself）*！

### 能力 3：有无可用的无头 AI 命令行

自动描述优化（`run_loop.py` / `run_eval.py`）通过 subprocess 调用无头 AI CLI，不依赖浏览器：

- 默认后端是 Claude Code 的 `claude -p`；如上文"描述优化"一节所述，描述改写可用 `SKILL_AGENT_CLI` 环境变量替换为其他"提示词进、文本出"的 CLI，触发测试则需要兼容 Claude Code `stream-json` 协议的命令。
- 建议等技能完全做完、用户认可状态良好之后再运行优化循环。
- 没有可用的无头 CLI 时，跳过自动描述优化。

### 打包（通用）

`package_skill.py` 只需要 Python 和文件系统，任何环境都能运行；默认在当前工作区的 `dist/` 目录暂存生成的 `.skill` 文件（目录不存在时创建），除非用户指定其他输出目录。打包完成后报告生成文件的绝对路径；把路径或下载链接告诉用户即可。

### 更新现有技能（通用）

用户可能是要你更新现有技能，而不是创建新技能。这种情况下：

- **保留原始名称。** 记下技能的目录名和 `name` frontmatter 字段——原样使用。例如，如果已安装的技能是 `research-helper`，输出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **编辑前先复制到可写位置。** 已安装的技能路径可能是只读的。先复制到系统临时目录（macOS/Linux 如 `/tmp/skill-name/`，Windows 如 `%TEMP%\skill-name\`），在那里编辑，然后从副本打包。
- **手动打包时先在临时目录中暂存**，再复制到输出目录——直接写入可能因权限失败。
