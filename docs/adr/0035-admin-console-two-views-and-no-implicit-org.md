# 管理后台为两类视角，组织不是隐式上下文

Status: accepted

修订 ADR-0032 的 Web 形态、落地 ADR-0033 的视角二分：管理后台只有两类视角——
Super Administrator 控制台与个人控制台，原 `/admin/org/*` 视角并入个人控制台。
个人控制台菜单四项：**概览（默认落地页）/ 我的组织 / 技能 / 邀请**。组织**不是
隐式上下文**：组织管理以「我的组织」列表为入口，对单个组织的一切操作都在 URL
里显式指名该组织。

## 背景与动因

1. 现状的 `org-admin` 是登录时对全组织做 `some()` 算出的投影
   （`packages/server/src/routes/auth.ts:66-70`），而"当前在哪个组织"由客户端取
   **第一个** org-admin 组织推断（`LoginView.vue:78`），全站没有组织切换器。
   角色是全局单值、治理是分资源的——用户属于两个组织时后台只能治理其中一个。
   这是模型错配的症状，不是实现疏漏。
2. 个人侧的技能视图必须是跨命名空间的（ADR-0032），而"个人技能不属于任何组织"
   需要一个**不特殊**的归宿：个人命名空间与组织命名空间在模型里是同一种东西，
   因此技能只按命名空间筛选，不另立"个人技能"入口。
3. 邀请与待审组织申请是跨组织、跨技能的**待办**，在旧的视角切分下没有归宿。

## Considered Options

- **组织切换器（组织区块内或顶栏全局）**：它保留一份可变的全局上下文，正是现状
  bug 的形状——刷新丢上下文、深链指向错误组织；弃。
- **为个人技能单开一个"我的技能"菜单项**：把命名空间的一种当成特例，与 ADR-0032
  "个人命名空间与组织命名空间同构"矛盾；弃。
- **组织详情页内嵌独立的技能列表**：同一份数据两处实现，必然分叉（两处显示与权限
  标注不一致）；弃——改为同一技能列表页锁定命名空间后的视图。
- **不设概览页，落地到某个功能页**：控制台落在自己的子区块上，且待办无处安放；弃。

## Consequences

- 个人控制台菜单：概览（落地）/ 我的组织 / 技能 / 邀请。概览聚合待办（待接受的
  邀请、待审的组织申请）、我的组织、我管理的技能。
- 「技能」= 跨命名空间技能列表页（命名空间筛选器，个人命名空间排最前）；组织详情
  页的「技能」页签是**同一个列表的锁定视图**（`?namespace=<org>`），同源实现、同源
  权限判定。
- 「我的组织」= 组织列表页：治理者见到治理入口与待审申请条目；非治理者见到只读的
  组织条目与自己在其中的团队身份。
- 组织详情页签为 **成员 / 团队 / 技能**（无"设置"页签——组织名不可改名是既定事实
  而非被隐藏的功能）；删除在详情页头部危险区（手打组织名确认，见 ADR-0034）；删除
  后回列表并以 `deleting` 标记呈现，不当场消失（`delete_failed` 必须被治理者看见）。
- Super Administrator 控制台的现有页面（首页、组织列表、组织详情含删除、组织申请、
  用户注册审批、全平台技能、技能管理、平台设置）全部保留，作为兜底与全局视图，
  删除入口不再是唯一路径。
- 邀请制补齐客户端：个人控制台「邀请」承载接受/拒绝，发起人可撤销——此后
  `member_add_mode: invite` 不再是"设置存在但功能不可达"的死配置。
- Web 侧角色枚举由 `'super' | 'org-admin' | 'member'` 收为两项；路由守卫与菜单改由
  两个独立判定驱动——**是否平台管理员**、**对该资源是否有治理权**——不再用一个
  全局角色值代理资源级权限。
