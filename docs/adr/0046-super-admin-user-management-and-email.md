# Super Administrator 用户管理与用户邮箱

Status: accepted

Super Administrator 获得面向 Skill User 的用户管理能力（列表、按用户名/邮箱查询、按启用禁用筛选、用户建号、禁用/启用、修改用户邮箱）。Skill User 新增必填的用户邮箱：全局唯一，用作联系属性与 Git Backend 提交匹配键，但不是登录标识。用户建号立即激活且绕过 `registration_mode`；用户禁用可逆、保留成员身份（含最后所有者），并立即失效既有登录态。

## 决策

- 用户管理对象仅为 Skill User；Super Administrator / 服务管理员账号不出现在用户列表，也不能被该流程建号或禁用。
- Super 控制台中「用户管理」与「用户注册审批」分立：前者管存量账号生命周期，后者管自助准入。
- 用户邮箱必填、全局唯一；登录仍只用用户名+密码。本人改邮须验证当前密码；超管改邮不消费目标用户密码。
- 用户注册与用户建号都必须写入合格用户邮箱；`approval` 待审申请同时占用用户名与邮箱。
- 存量合成邮箱不洗白为合格用户邮箱，记为「邮箱待补全」：仍可登录并正常使用，仅标记/提醒，由本人或超管补全。
- 用户建号不受 `registration_mode` 约束；是否强制首登改密由平台设置「建号首登改密策略」决定，出厂默认强制，并在建号当时快照到该账号。
- 用户禁用 = 禁止登录并立即失效 Token/会话；不删号、不释放命名空间、不解除组织身份。禁用最后一名所有者成员被允许，组织治理靠 Super Administrator 兜底。

## 考虑过的方案

- **用邮箱登录**：与既有 Skill User Credential（用户名+密码）及个人命名空间=@用户名模型冲突，认证面扩大；弃。
- **联系邮箱与 Git 匹配邮箱分离（一人两邮）**：能保留历史合成邮箱约定，但运维与心智双倍，改邮不同步；弃。
- **禁用即删除或释放用户名**：不可逆，且与组织成员/技能 Maintainer 关系纠缠；本轮明确不做。
- **禁止禁用最后所有者**：把账号禁用耦合成隐式组织约束；弃，改由超管组织治理兜底。
- **邮箱待补全硬门闩（未补全不能办事）**：迁移期过猛；首发保持软标记，硬门闩可另立项。

## 后果

- 注册、建号、资料与超管用户管理都要采集/展示/校验用户邮箱；Gitea 侧不再以合成邮箱冒充产品层用户邮箱。
- 平台设置增加建号首登改密策略；与用户注册模式一样由 Super 控制台配置。
- 组织「最后所有者被禁用」成为可预期状态：成员侧可能暂时无人可登治理，超管必须能继续操作该组织。
