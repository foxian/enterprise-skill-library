# 技能依赖采用版本提示与用户自主清理

Status: proposed

技能依赖主要表达安装时需要补齐的技能，而非不可拆分的运行时绑定。经用户确认，消费端应允许独立更新传递依赖，版本超出依赖方声明范围时只提示、不阻止主动升级；卸载时由用户明确选择是否清理关联依赖，不再无条件回收。本决策尚未实现，整体设计仍在讨论。

## 已确认的规则

- 保留同一 Skill Identity 在一份安装环境中只有一个版本的模型，不引入嵌套多版本。
- 安装根技能时自动补齐其声明的依赖链。
- 新安装根技能时优先复用环境中已安装的共享依赖，即使超出新根的声明范围，也只提示差异，不自动降级或替换；缺少的依赖才安装。复用不代表已验证功能兼容。
- 自动安装的传递依赖可单独更新，无须同时更新依赖它的根技能；独立更新不自动将其变为直接安装项。
- 用户主动更新时，版本范围属于兼容性提示。目标超出范围时展示受影响技能，不要求额外强制确认，也不改写作者的依赖声明；这不表示系统已验证能力兼容。
- 卸载根技能时列出不再被其他技能需要、且非用户直接安装的关联依赖，供用户多选清理。默认全部不勾选，提供全选入口，只删除用户选中的项目。
- 仍被其他技能需要或由用户直接安装的技能不作为默认清理候选，不随根技能自动删除。
- 更新根技能后不再需要的依赖沿用卸载时的清理选择：列出候选，默认不勾选，不静默删除。
- 用户选择保留的依赖应持续保留，不得在之后的更新中作为孤立依赖静默回收。如何持久化保留意图仍待设计。
- 用户主动单独卸载仍被依赖的技能时，提示受影响技能，明确确认后允许删除；不连带删除依赖方，并呈现依赖缺失状态。
- 作者声明的依赖关系、环境实际安装版本与依赖是否缺失是不同信息，不应混写或假装声明范围已经满足。
- 作者默认只声明所需 Skill Identity；operator 不主动补版本，CLI 不根据当前最新版本推导版本约束。未指定版本时使用现有清单格式中的 `*` 表示不限稳定版版本号，解析时选择符合条件的最高稳定版本。
- 作者明确指定版本或范围时原样保存，发布端按该要求解析；无匹配版本则提示作者修改并停止发布，不自动越界，也不擅自改写声明。
- 发布时仍冻结实际选中的具体版本以便追溯；冻结记录不等于给作者补上版本范围。用户后续主动升级仍遵循超范围只提示的消费端规则。

- `update` / `uninstall` 应接入 ADR-0043 的 `--agent-interaction` 协议，AI 与人工终端遵循相同的清理选择和删除影响确认规则，默认不勾选关联依赖。
- Agent 模式需要选择时，CLI 在删除前输出结构化问题并以退出码 2 结束；AI 收集用户答案，通过命令支持的参数重跑，CLI 重新校验影响后执行，不把模式开关当成删除授权。
- 未启用 Agent 协议的无人值守脚本默认保留关联依赖；删除仍被其他技能依赖的目标，需要显式确认影响，否则不执行该删除。

## 对既有约定的影响

本提案拟修订 ADR-0056 中消费端范围冲突必须失败、孤立依赖自动回收的规则，保留其单身份单版本约束。ADR-0056 当前仍记录已有实现；本提案不代表相关行为已上线。发布端保留对显式版本要求的校验及具体版本冻结；不采用找不到匹配版本时自动越界的方案。

## 待确认的边界

- 保留意图和依赖缺失状态的持久化方式。
- 既有依赖声明保持原样，不因新默认值而自动改写；若要将示例技能的已有范围改为 `*`，应作为明确的技能源修改执行。

实现时必须同步内置 `skills/esl-operator/` 的说明与参考文档，并验证更新、安装、卸载及后续回收行为。
